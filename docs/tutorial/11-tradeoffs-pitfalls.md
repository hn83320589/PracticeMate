# 11 設計取捨與踩坑紀錄

這一章保存最難從程式碼看出來的知識：當時為什麼這樣選、走過哪些死路。素材來自設計文件、commit 訊息、測試報告與開發對話。

## 設計取捨

### T1：音高用 MPM 選週期 + DTFT 精修，而不是單一演算法

- **決策**：MPM 負責「選對週期」，`HarmonicFrequencyRefiner` 負責「量準頻率」。
- **考慮過的選項**：單純 MPM／YIN；MPM 加 lag 域 Newton 精修；自相關前扣除頻譜雜訊底；頻域泛音精修。
- **選擇與理由**：只有頻域精修達到 ≤ 1 音分（見踩坑 P1）。📄 commit `e61335e`、設計文件 §5.2
- **代價**：運算量約增加一倍，精修成為分析最耗時的階段（每幀約 0.7 ms），必須平行化才能符合 10 秒的要求。

### T2：分析視窗 80 ms、調音器視窗 40 ms

- **決策**：同一套偵測器，分析用 4096 點，調音器用 2048 點。
- **理由**：分析重精度（55 Hz 純音也要 < 1 音分），調音器重延遲（≤ 100 ms）。📄 README「設計取捨」
- **代價**：調音器在 55 Hz 純音約有 2.4 音分誤差（中位數），寫入 README 已知限制。

### T3：調音器的泛音精修減量（6 → 4 個泛音、3 → 2 次迭代）

- **決策**：`PitchDetectorOptions` 新增 `RefinementHarmonics`、`RefinementIterations`，分析維持預設，調音器減量。
- **理由**：驗收時發現調音器單區塊時間的 p99 為 0.74–1.17 ms，偶發 3.2 ms（`docs/test-report.md` F2）。使用者選擇優化。📄 開發對話「調音器照你的建議優化」；commit `4fbfa96`
- **代價**：精度幾乎不變（中位數最差 0.49 音分），先寫了 `TunerAccuracyTests` 量出優化前的基準才修改。結果：中位數 0.31 ms、p99 0.53–0.75 ms。單次最大值仍偶爾約 1 ms，那是作業系統排程造成的，減少運算消除不了。

### T4：節拍器 BPM 限定為整數

- **決策**：節拍器 BPM 為 30–300 的整數；節拍報告的 BPM 允許小數。
- **理由**：讓 round(k·60·fs/BPM) 能全部以整數運算，絕不漂移（08 章第 7 節）。📄 規格解讀 Q3
- **代價**：無法設定 92.5 BPM 這類速度。對練習用途影響很小。

### T5：環狀緩衝區溢位時整塊丟棄新資料

- **理由**：保持交錯聲道對齊；規格要求「丟棄新資料、不覆寫舊資料」。📄 規格解讀 Q4
- **代價**：溢位時遺失的是一整個 WASAPI 區塊（約 10 ms），而不是剛好多出來的部分。實務上 2 秒緩衝很少溢位，且溢位次數會顯示在畫面上。

### T6：預設裝置變更只在「跟隨系統預設」時停止錄音

- **理由**：使用者明確選了 USB 麥克風時，插上耳機（系統預設改變）不應中斷錄音。📄 規格解讀 Q5

### T7：擷取消費者是同步的 `Pump()`

- **理由**：讓錄音、當機、拔除、溢位的所有情境都能確定性地測試。📄 README「設計取捨」、設計文件 §4.1
- **代價**：多一個 `CapturePumpRunner` 類別負責在正式環境中定期呼叫；Pump 週期（5 ms）是固定值。

### T8：檔頭依「取樣數」更新，不依牆上時鐘

- **理由**：行為確定、可測試；不受系統時間調整影響。📄 README「設計取捨」
- **代價**：無。這是少數沒有代價的選擇。

### T9：自寫性質測試工具，不用 FsCheck

- **理由**：需求只有固定種子與可重現的失敗訊息，少一個依賴。📄 設計文件 §10
- **代價**：沒有 shrinking；種子固定，不會自動探索新的輸入。

### T10：頻譜圖以 8 位元 dB 儲存

- **理由**：10 分鐘 48 kHz（2048 點、75% 重疊）用 `double` 會超過 400 MB，8 位元約 58 MB。顯示只需要約 0.5 dB 的解析度。📄 README「設計取捨」
- **代價**：無法從頻譜圖資料做精確的數值分析，但分析本身不使用頻譜圖。

## 踩坑紀錄

### P1：MPM 在雜訊下有 2–3 音分的系統偏差

- **症狀**：技術驗證（spike）時，MPM 在無雜訊時幾乎完美（≤ 0.03 音分），但加入 20 dB 白雜訊後，低音純音誤差達 2–3 音分，遠超 1 音分的要求。
- **原因**：白雜訊的「雜訊×雜訊」自相關在相鄰延遲之間快速變動，把 NSDF 寬峰的頂點拉偏約 1 個取樣。55 Hz 的週期約 873 個取樣，偏 1 個取樣就是約 2 音分。
- **嘗試過的解法**：
  1. lag 域三角多項式 Newton 精修：無改善，因為偏差在峰形本身。
  2. 自相關前扣除頻譜雜訊底：改善有限，最差仍 1.6 音分。
  3. **採用**：改到頻域，在各泛音上用 Newton 法求 DTFT 功率極大值。
- **對應**：commit `e61335e`；`src/PracticeMate.Core/Pitch/HarmonicFrequencyRefiner.cs`
- **教訓**：最高風險的驗收項目先做 spike。這次在 M5 的第一步就發現問題，若到最後整合才發現，影響範圍會大得多。另一個教訓是「選週期」和「量頻率」可以拆開，各自用最適合的方法。

### P2：峰值包絡讓起音晚 5–13 ms

- **症狀**：起音精修後，低音的起音時間仍晚 5–13 ms。
- **原因**：原本的包絡是每 1 ms 一格的峰值。低音的週期長於 1 ms 時，很多格抓不到波峰，包絡呈鋸齒狀，門檻交會點落在較晚的格子。
- **解法**：改用以每格為中心的 10 ms RMS 視窗。commit `91b8040`
- **附帶的坑**：測試合成器的撥弦／打擊在截斷處產生喀聲，被**正確地**偵測為多餘的起音。修正方式是在截斷處加 10 ms 淡出。
- **教訓**：測試失敗時，要先判斷錯的是受測程式還是測試訊號。

### P3：`.gitignore` 範本誤擋整個 App 專案

- **症狀**：`src/PracticeMate.App` 目錄沒有被 commit。
- **原因**：Visual Studio 的 `.gitignore` 範本有 `*.app` 規則（macOS 應用程式套件），Windows 檔案系統不分大小寫，`PracticeMate.App` 被當成符合。
- **解法**：移除該規則。commit `bed8cbb`
- **教訓**：專案或目錄名稱以 `.App`、`.Build` 等結尾時，檢查 `.gitignore` 範本的萬用字元規則。

### P4：環狀緩衝區測試在 Windows 上逾時

- **症狀**：小容量的跨執行緒測試偶爾逾時。
- **原因**：測試的等待迴圈用 `SpinWait`，它在自旋一定次數後會呼叫 `Thread.Sleep(1)`，而 Windows 的計時器解析度約 15 ms，實際睡了 15 ms。
- **解法**：`SpinOnce(sleep1Threshold: -1)` 停用 `Sleep(1)`。commit `cce01a0`
- **教訓**：`Sleep(1)` 在 Windows 上不是 1 ms。

### P5：顫音讓音準中位數偏離

- **症狀**：驗收 #10（刻意走音音階，含輕微顫音）偏差誤差接近上限。
- **原因**：規格要求取「中間 60% 時間」的中位數。這段時間不是整數個顫音週期時，中位數會偏離中心約 0.3 × 顫音深度。
- **處置**：這是規格定義的行為，不是程式錯誤。測試使用 ±5 音分的顫音（偏離約 1.1 音分，在 2 音分容許內），並寫入 README 已知限制。
- **教訓**：照規格實作仍可能有統計偏差，要寫清楚，而不是悄悄改演算法。

### P6：測試訊號本身違反假設

- **症狀**：真峰值測試與長靜音閘控測試失敗。
- **原因**：(1) 突然開始的正弦在帶限重建下真的會過衝，所以真峰值本來就比理論值高；(2) 含長靜音的訊號，交界處的 400 ms 區塊會被部分閘掉，比較結果受區塊對齊影響。
- **解法**：正弦改為淡入淡出；閘控比較改用較長的訊號以稀釋交界區塊的影響。commit `84b8171`
- **另一項**：8 kHz 的 K 加權響應與 48 kHz 差約 0.2 dB（雙線性頻率扭曲），該測試被移除，改在 README 註明。分析前會先轉成 48 kHz，所以不影響實際結果。

### P7（F1）：PNG 匯出位移或整張空白

- **症狀**：驗收測試時匯出的圖表 PNG 有白邊，放在第二列的音準長條圖整張空白。
- **原因**：`RenderTargetBitmap.Render(element)` 會套用元素在父元素中的位移。ViewModel 測試使用假的匯出器，所以沒有抓到。
- **解法**：改用 `VisualBrush` 把元素畫到原點的 `DrawingVisual`，再渲染。新增 `tests/PracticeMate.App.Tests/ChartImageExporterTests.cs` 在 STA 執行緒上實際繪製，修正前失敗、修正後通過。commit `7aee111`
- **教訓**：假實作只能驗證「有被呼叫」，驗證不了「做得對」。和平台 API 互動的那一層至少要有一個實際執行的測試。

### P8（F4）：起音被前一個音的餘音拉早約 40 ms

- **症狀**：驗收後的外部檢閱發現，新音不比前音餘音大時（殘響、漸弱、同音連續吐音），起音固定提前約 40 ms，節拍報告會誤判為「搶拍」。
- **原因**：精修時在通量峰值 ±40 ms 內找包絡最大值。新音不比餘音大時，最大值落在視窗最前端的餘音上，回溯第一步就成立，結果正好回傳「通量峰值 − 40 ms」。測試合成器的音量全部相同，新音一定遠大於餘音，所以從未觸發。
- **解法**：先擴充合成器（每音音量、不截斷餘音、Schroeder 殘響）重現問題，再修改精修規則（08 章第 3 節的四條）。隨機 1500 個起音的測試中，誤差 > 10 ms 由 1.47% 降到 0.20%，不再有提前的情況。commit `87dc795`
- **未解決**：剩下的 0.2% 延後 10.5–16.2 ms。三次調整後依專案規則停下回報，是否改成分頻帶偵測待使用者決定。
- **教訓**：
  1. 合成測試只能測到合成器能產生的情境。設計測試訊號時要刻意加入「對演算法不友善」的條件。
  2. 外部檢閱者用自己的訊號測試，比作者自己的測試更容易找到盲點。

### P9：UI Automation 驅動實際程式的坑

驗收時用 PowerShell + UI Automation 驅動真實的程式（單一執行個體、錄音、強制結束程序測試當機安全）。

- `MessageBox` 在 UI Automation 樹中的控制項類型是 Pane，不是 Window。
- 「另存新檔」對話框的擁有者是主視窗，要從主視窗底下找，不是從桌面根節點找。
- PowerShell 變數不分大小寫，`$t` 會覆蓋 `$T`。
- 檔案對話框的檔名欄位在中文輸入法啟用時無法用 UI Automation 或 SendKeys 輸入，嘗試兩次後放棄，改為直接測試匯出器、對話框以人工確認。
